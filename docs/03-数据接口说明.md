# 数据接口说明

> 面向 Web 与安卓端共用的数据契约。两端使用**同一次构建产出的同一份数据**，保证数值与结构完全一致。

---

## 一、产物与消费方式

| 产物 | 消费方 | 说明 |
|---|---|---|
| `index.html` | Web | 自包含单文件，数据内联，离线可用 |
| `shared/app-data.json` | 安卓端 / 其它消费方 | 独立 JSON，缩进格式，便于阅读与调试 |
| `shared/app-data.min.json` | 安卓端 | 同内容的紧凑版，体积约少 25% |
| `data/fixed-prices.json` | **唯一数据源** | 改价格只改这里，然后重新构建 |

三者由 `node tools/build.mjs` 一次产出，**不要手工修改 `shared/` 与 `index.html`**——它们是构建产物。

安卓端有三种取数方式，实测均可用：

| 通道 | 地址 / 方式 | 适用 |
|---|---|---|
| ① 随包内置 | 把 `shared/app-data.min.json` 放进 RN 工程 assets，启动时读取 | **离线优先，推荐作为兜底** |
| ② 站点同目录 | `https://interprovince-route.app.workbuddy.host/shared/app-data.json` | 已随 Web 版一起部署，返回 `application/json` |
| ③ CDN 拉取 | `https://cdn.jsdelivr.net/gh/ChenShi-Tech/interprovince-route-optimizer@main/shared/app-data.json` | 国内可达，返回 `application/json`；仓库更新后自动生效 |

> 另有 GitHub raw（`raw.githubusercontent.com`）也可取到，但国内访问不稳定，不建议作为主通道。

推荐做法是**两者结合**：内置一份作兜底，联网时用 ② 或 ③ 比对 `priceVersion`，不一致再刷新。

> ⚠️ 输出目录**不要用 `dist/`**：发布工具会把它当作构建产物排除，导致站点上 404。本项目的输出目录因此取名为 `shared/`。同目录下的 `README.md`、`data/`、`docs/` 均已验证可正常访问。

> 💡 若将来接入 WorkBuddy 云服务（数据库 / 登录 / 存储），本文件的字段结构可直接作为 `tariffs` 表的设计基础：`tier`、`doc`、`eff`、`excerpt` 已具备版本与溯源的语义，补充 `valid_from` / `valid_to` / `verified_by` 即可满足审计要求。

## 二、版本与完整性

```json
{
  "schema": "iproute-app-data/v3",
  "builtAt": "2026-09-14T09:20:00.000Z",
  "priceVersion": "96078954f87aff52",
  "dataHash": "800759640231da83…",
  "counts": { "stations": 91, "channels": 70, "sections": 10, "provinces": 30 }
}
```

| 字段 | 用途 |
|---|---|
| `schema` | 结构版本。字段增减时递增，消费方据此做兼容判断 |
| `priceVersion` | **价格数据指纹**，由 `data/fixed-prices.json` 的内容哈希得出。只要价格变了这个值就变 |
| `dataHash` | 载荷指纹，用于校验传输完整性 |
| `counts` | 快速自检：条数与预期不符说明数据不完整 |

Web 端把 `priceVersion` 渲染在「费率库 → 数据管理」中，两端可直接肉眼比对。

**版本不一致时不要混用两端数据**——同一笔交易在两个端算出的落地价会因为费率版本不同而不一致，这比算出错误结果更难排查。

## 三、数据结构

### `ST` 站点（换流站 / 变电站）

```ts
type Station = {
  n: string;    // 名称，如「锦屏换流站」
  a: string;    // 精确站址，如「四川凉山州西昌市裕隆乡」
  lng: number;  // 经度（县/市级近似，原文可到乡镇/村级）
  lat: number;
  p: string;    // 所属省代码
};
```

用途：地图打点、路径落点展示。**91 个站点已覆盖主要换流站，非全部。**

### `CH` 通道（跨省输电通道）—— 核心

```ts
type Channel = {
  id: string;
  n: string;          // 通道名
  fn: string;         // 别名，多个用 / 分隔
  from: string;       // 送端省代码
  to: string;         // 受端省代码
  stFrom: string|null; // 送端换流站 id（指向 ST）
  stTo: string|null;   // 受端换流站 id
  kv: string;         // 电压等级，如 ±800kV
  type: 'DC'|'AC';
  loss: number;       // 线损率 %
  t: number|null;     // 输电价 元/MWh（容量制工程为折算的等效度电成本）
  tRaw: number|null;  // 发改委核定原值；容量制工程为 null
  sendFee: number;    // 送端省内段费用（送出省输电价格）元/MWh
  cap: number|null;   // 用于容量校验的容量，优先取实际输送能力
  capRated: number|null;   // 额定容量
  capActual: number|null;  // 实际输送能力
  capBasis: 'cap'|'rated'|'unknown';  // cap 的取值口径
  capSrc: string;     // 容量来源说明
  priceType: 'energy'|'capacity';     // 计价方式
  capPrice: object|null;              // 容量制工程的容量电价与文号
  capEq: number|null;                 // 容量制折算的等效度电成本
  tier: 'gov'|'grid'|'region';        // 数据可信度
  doc: string;        // 核定文号
  eff: string;        // 生效日期
  bill: string;       // 计费口径
  tax: boolean; incLoss: boolean;
  sendFee: number;
  excerpt: string;    // 原文摘录
  hist: Array<{ effective_from, tariff_raw, loss_rate_pct, doc_number, note }>;
  tradable: boolean;  // 是否属于省间现货交易网络（交流联络线为 false）
  bidir: boolean;     // v2：能否双向通行。单向送电直流 false；德宝、青藏、长南荆、辛洹、灵宝、高岭、云霄与全部联络线 true
  regional: boolean;  // v2：是否属区域共用网络（仅联络线 true）；过境非买方区域时按该区域计电量电价
  tRev: number|null;  // v2：联络线反向行进时的输电价（对侧省的送出省输电价格）；专项工程 null（核定价与方向无关）
  sendFeeRev: number|null; // v3：双向专项工程反向行进时的送端省内段费用（对侧省的送出省输电价格）；其余 null
  dirNote: string;    // v3：方向依据（公开报道 / 文件编号）
  marginalNote: string;    // v3：容量制工程边际输电价的说明（辛洹 0、云霄输电权下限）
  status: string; note: string; sourceIssue: string|null;
};
```

`schema` 由 v1 升到 v2 增加了 `bidir` / `regional` / `tRev`，v3 增加了 `sendFeeRev` / `dirNote` / `marginalNote` 与 `PV` 的三个线损字段，其余字段不变。

### `PV` 省级参数

```ts
type Province = {
  n: string; lng: number; lat: number;
  clear: number|null;   // 现货出清价 元/MWh（示例值，需按行情替换）
  net: number|null;     // 受端省网输配电价 元/MWh（220kV 及以上两部制）
  fund: number|null;    // 政府性基金及附加 元/MWh。**可能为 null**
  netSrc: string;       // 取值依据与文号
  inLoss: number|null;      // v3：省内上网环节线损率 %（1077号附件1 注3），受端用户承担，进完整落地价
  exportLoss: number|null;  // v3：送省外上网环节线损率 %（注4），卖方承担，只进口径三
  exportKind: string|null;  // v3：送出省价格口径：「核定外送」或「临时互济条款」
};
```

⚠️ **`fund` 为 `null` 表示该省官方未列出分项标准（当前仅西藏）。消费方必须按「缺失」处理并提示用户，不要静默当作 0** —— 那会低估落地成本。

### 其余

- `SEC` 断面：`{ id, n, edges[], limit, note, src }`
- `RG` 区域电网输电价格（电量电价，元/千瓦时）：`{ 华北, 华东, 华中, 东北, 西北 }`
- `RGOF` 省→区域归属，联络线段按到达省所在区域取区域电网电量电价

## 四、算法约定（不在数据文件内，需消费方实现）

数据文件只提供数据，**路径规划算法需自行实现**。约定如下，与 Web 版保持一致：

### 落地成本公式

```
省界价(元/MWh) = 出清价 × (1 + g × 网损电量)
               + Σ [ sendFee_i × 段前系数_i ]        送出省段按其出口电量（= 本段入口电量）
               + Σ [ t_i × 段后系数_i ]              所有段按段后电量（S14 规则 4.3.1）
               + 买方区域电量电价 × 1
               + Σ [ 过境区域电量电价 × 段后系数_i ]   regional=true 且到达省不在买方区域的联络线段
落地价         = 省界价 × (1 + ρ受/(1−ρ受))        ρ受 = PV[受端].inLoss（上网环节线损）
               + 受端省网输配电价 + 政府性基金及附加
```

其中 `t_i`、`sendFee_i` 按实际行进方向取值：联络线反向为 `tRev`，双向专项工程反向为 `sendFeeRev`。

**可选口径：只算到受端省界。** 若不需要受端省内费用（用于与「送到省界」的口径对齐），把上式末尾两项置零即可：

```
送到省界价 = 上式的「省界价」（不加受端上网环节线损、省网输配电价与基金附加）
```

- 两种口径只差受端省内三项：`PV[受端省].net + PV[受端省].fund + 省界价 × ρ受/(1−ρ受)`，其余费用项与所选路径完全不变
- **过网费（口径二）与送端净收益（口径三）不受该开关影响**，因为它们本就不含受端省内费用
- 费用表的各项之和必须等于合计、合计 ÷ 电量必须等于单价——两种口径下都要成立

其中：

- **送达系数** `D = Π(1 − η_i/100)`，η 为该段线损率
- **段前系数** `1 / Π_{j≥i}(1 − η_j/100)`：越靠送端的段，承担的电量与损耗越多
- **网损电量** `= 1/D − 1`（每交付 1 MWh）
- `g` = 受端承担的网损比例（受端承担 1 / 各半 0.5 / 送端承担 0）
- **段后系数** `1 / Π_{j>i}(1 − η_j/100)`：该段落地端（段出口）每交付 1 MWh 对应的电量
- **两条系数链**：物理链用全部段的核定线损率（功率、容量占用、物理损耗）；计费链把 `incLoss=true` 的段线损按 0 计——《省间电力现货交易规则》(2026-04) 3.3.2「输电价格已包含网损的，不再另行收取」。`D`、段前 / 段后系数、网损电量均指计费链
- **输电费的计量电量**：所有段按段后电量——规则 4.3.1 折算公式 `Σ Pt_m × Π_{r≤m}(1−ρ_r)`，换算到每交付 1 MWh 即输电价 × 段后系数；与 3.3.1「专项工程按实际物理计量电量结算」、1490号附件4第十八条「落地端结算电量」一致
- **区域电网电量电价**：买方所在区域一律计一次（规则 3.4.2(a)「统一计入买方节点所在区域电网的输电价格和网损」；发改价格规〔2020〕1441号第二条），取 `RG[RGOF[受端省]] × 1000`；路径过境其它区域的 `regional=true` 联络线段再按该区域计 `RG × 1000 × 段后系数`。区域电网自身网损率未公开，按 0
- **省内线损**：送端 `PV[送端].exportLoss`（送省外上网环节线损率）由卖方承担（规则 7.3(a)），只进口径三：卖方成本 = 出清价 × 段前系数₀ × ρ送/(1−ρ送)；受端 `PV[受端].inLoss` 进完整落地价
- **行进方向**：`bidir` 逐条由数据给定；反向行进时联络线 `t` 取 `tRev`，双向专项工程 `sendFee` 取 `sendFeeRev`，绕行度起点按实际行进方向
- **容量制工程**：`t` 为交易方的边际输电价（辛洹 0，云霄 25.6 输电权报价下限），`capEq` 仅供展示

**网损是乘法项，不能直接作最短路边权。** 建议两步：先用线性近似 `t + sendFee + 线损率×出清价 + 区域费` 求候选路径，再用上式精确重算排序。

### 三种口径

| 口径 | 目标 | 含义 |
|---|---|---|
| 一 · 受端落地成本 | 最小 | 买方视角的综合最优 |
| 二 · 过网费 | 最小 | `Σ sendFee × 段前系数 + Σ t × 计量系数`，不含网损、区域电网费与省网费用 |
| 三 · 送端折回净收益 | 最大 | `受端结算价 × D − 过网费 × D − 网损成本 × (1−g) × D` |

### 路径约束（依据《省间电力现货交易规则》3.2 条）

1. **不重复经过同一交易节点** → 只枚举简单路径
2. **优先选择输电价格最低的交易路径** → 按成本劣化阈值收敛（Web 版默认 10%）
3. 交易节点为**省级电网**（1 省 1 节点），不是变电站
4. **通道方向逐条由 `bidir` 给定**：单向送电直流只按核定方向（1490号附件4第二条「送受端相对明确、潮流方向相对固定」）；德宝、青藏、长南荆、辛洹、灵宝、高岭、云霄经公开报道证实双向运行（`dirNote`），联络线双向
5. **必经通道组件**（可选，Web 版为 `input.mustHave`）：用户指定的通道 id 数组，路径须**全部包含**其中每一条。它作用在枚举与绕行度筛选**之后**，只收窄结果，不参与任何计价或排序；同一条通道不论正向还是反向经过都算命中，方向仍由 `bidir` 决定。id 取自 `CH[].id`，**旧存档里已不存在的 id 要忽略，而不是把结果筛成空**。

Web 端的「通道组件」选择器即这条约束的界面：候选清单取自已通过绕行度筛选的**完整候选集**（不是最终结果），因此选中一个组件后其余组件仍可点选、可取消，用户不会被自己的选择困住。

### 容量校验

```
段 i 入口功率 = 交付电量 / 时段长度 / 段前系数_i
可行条件：段入口功率 ≤ CH[i].cap（capBasis 为 unknown 时应提示结果偏乐观）
```

## 五、数值回归

`docs/regression-baseline-v2.json` 记录了 331 个省对、693 条路线的完整数值结果，可作为手机端算法的回归基准：**实现完成后，同一输入应产出同一输出。**

Web 版用 `node tools/baseline-check.mjs` 校验。手机端可将同一组用例写成单测对照。
