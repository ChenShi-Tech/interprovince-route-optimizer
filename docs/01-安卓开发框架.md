# 安卓端开发框架建议

> 面向「省间电力现货交易路径优选测算」工具。结论先行，理由在后。
>
> **当前状态（2026-09-14）**：本文是**技术选型与架构建议**，安卓端**尚未开始编码**。
> 已就绪的是**数据层**——`shared/app-data.json` 与 Web 版同源同版本，字段与算法契约见 [数据接口说明](./03-数据接口说明.md)，
> 回归基准见 [regression-baseline-v2.json](./regression-baseline-v2.json)。

## 一、先看一个决定性事实

当前测算网络是 **30 个省级节点、70 条通道**（46 条专项工程 + 24 条省间联络线）。在这个规模下，路径枚举 + 乘性网损精算在手机上**毫秒级完成**（实测全量 295 个省对、688 条路线的基线扫描在 Node 里不到 1 秒）。

推论有三条，每一条都在推翻默认架构：

1. **一期完全不需要服务器。** 计算全在端侧，费率库随包发或手动导入。
2. **没有网络也能算。** 交易员在谈判桌、变电站现场、信号差的酒店都能出结果——这是真正贴合使用场景的优势，不是技术炫技。
3. **没有服务器成本与运维。** 一期是一个纯客户端项目，交付物就是一个 APK。

服务端只在出现「多人共用同一份费率库 + 变更留痕 + 行情自动同步」这个需求时才引入。这属于二期，不要提前做。

## 二、技术选型（明确推荐，不罗列）

### 主选：React Native + Expo（TypeScript）

| 层 | 选型 | 理由 |
|---|---|---|
| 框架 | React Native + Expo SDK | 打包出 APK 一条命令，内部分发不走应用商店 |
| 语言 | TypeScript（strict） | 算法可单测，与团队前端背景零摩擦 |
| 状态 | Zustand | 够用，不要上 Redux |
| 本地库 | expo-sqlite | 费率库离线存储 + 行情缓存 |
| 图表 | react-native-svg + gifted-charts | 成本拆解堆叠条、方案对比表 |
| 地图 | WebView 内嵌腾讯地图 GL JS | 现有地图代码直接复用，天然合规 |
| 算法 | 独立纯 TS 包 | 端侧调用，无依赖，Node 里可跑回归 |
| 单测 | Vitest | 用真实案例做回归基线 |
| 打包 | Expo EAS → APK | 内网 / 钉钉群分发 |

### 为什么是 React Native 而不是 Flutter

按重要性排序，第一条就足够决定：

1. **算法零改动复用。** 现有原型里的图构建、按近似成本排序的简单路径枚举、乘性网损精算都是**纯函数、零依赖**，可以直接搬进独立包。这是项目最大的既有资产，也是唯一经过实测验证的部分（修掉了对向边方向错误、跳数绕行失控两个真实缺陷）。Flutter 要用 Dart 全部重写，等于把验证过的逻辑重新引入风险。
2. **团队是前端背景。** TypeScript 直接上手，没有学习成本。这个项目后续要做费率库编辑、版本对比、导入导出这些偏表单与数据处理的活，RN 生态更顺手。
3. **打包分发简单。** Expo EAS 一条命令出 APK，内部分发不需要软著、不需要备案、不需要走应用商店审核。
4. **地图可以完全复刻。** 用 WebView 内嵌腾讯地图 GL JS，现有地图页代码原样搬进去，同时天然满足合规要求（省界由合规底图负责，自己一帧都不画）。

### 什么情况下改选 Flutter

- 确定未来一定要出 iOS 版本，且不想维护两套；
- 对地图渲染与动画性能有硬要求（例如要在图上做大量实时动画）；
- 团队里已经有人熟练 Dart。

代价是：算法全部重写为 Dart，需要重新建立回归测试基线。**如果选 Flutter，务必先把算法逻辑用真实案例跑出一组基线数值，再用 Dart 对着这组基线写测试**，否则重写过程中的口径漂移无法察觉。

### 什么情况下选原生 Kotlin + Jetpack Compose

只在「只做安卓 + 需要后台常驻、深系统集成（推送、定位、蓝牙）」时选。本项目不需要，不建议。原生地图 SDK 支持虽然最完整，但节省的开发效率被 Dart/Kotlin 的学习与重写成本吃掉。

## 三、工程结构

```
apps/mobile/           React Native 应用
packages/engine/       纯 TS 算法：图构建 / 最短路 / K 短路 / 网损精算
packages/tariff/       费率 schema、单位换算、导入校验、版本规则
packages/ui/           共用组件（可选）
tools/                 费率导入脚本、数据校验 CLI
docs/                  本目录
```

**硬约束：`packages/engine` 不得 import 任何 RN、UI 或网络库。** 它是端侧与服务端共用的同一份代码，也是唯一可以在命令行里快速回归的部分。这条纪律一旦破了，算法就再也没法脱离 UI 单独验证。

## 四、三条不可妥协的工程纪律

### 1. 费率必须版本化

每条费率记录至少要有四个字段：

```
valid_from      生效日期
valid_to        失效日期（可空，表示现行有效）
source_doc      核定文件文号，如「发改价格〔20XX〕XXX号」
verified_by     复核人
```

理由很直接：发改委每调一次价、核一次线损率，历史测算就换了答案。没有这四个字段，**任何历史测算都无法复现，也无法向审计解释「为什么上个月算出来是另一个数」**。这是这类工具唯一不可让步的设计。

### 2. 算法与 UI 分离

见上文硬约束。收益是：算法可以在 CI 里跑、可以用真实业务案例做回归、可以在 Node 里做全量组合扫描（本次开发就是靠这个发现了「三口径零分歧」这个结论）。

### 3. 计算可复现

每次测算结果都要留痕：输入参数 + 费率版本号 + 引擎版本号。任何一次结果都能原样重算。这一条是给审计和复盘用的，不是给技术用的。

## 五、从现有原型的迁移路径

| 步骤 | 做什么 | 验收标准 |
|---|---|---|
| 1 | 抽出 `packages/engine`，从原型直接搬算法 | 补 30+ 单测，用真机实测数值做回归基线 |
| 2 | 费率库从 JSON 迁到 SQLite，加 schema 校验与版本号 | 导入一条错误数据能被拦住并指出原因 |
| 3 | 搭 RN 壳，落地测算页 + 结果拆解页 | 与原型输出数值完全一致 |
| 4 | 地图页改为 WebView 内嵌合规地图 | 通道与最优路径高亮正常，无 SDK 时降级 |
| 5 | 费率库编辑页 + 导入导出 | 改一条费率，重算结果同步变化 |
| 6 | 出 APK，内部试用 | 真机安装、离线可用 |
| 7 | 二期接后端做费率同步与版本审计 | 版本变更可追溯 |

**第 1 步的基线数值是整个迁移的安全网。** 已导出为 `docs/regression-baseline-v2.json`（295 个省对、688 条路线，含费率快照 sha256）。后面无论用 RN 还是 Flutter，都拿它当回归基准——同一输入必须产出同一输出。Web 版用 `node tools/baseline-check.mjs` 校验，安卓端建议把同一组用例写成单测对照。算法约定见 [数据接口说明](./03-数据接口说明.md) 第四节。

## 六、安卓内部分发怎么做

- `eas build -p android --profile preview` 产出 APK；
- 放到公司内网共享盘、钉钉群或企业微信分发（你们已有钉钉生态，这条最省事）；
- 启动时比对版本号，提示升级；
- 不需要上国内应用商店；真要上商店则需要软件著作权登记与 App 备案，属于额外数周量级的行政流程，非技术问题。

---

## 七、一句话总结

**React Native + Expo 做壳，算法抽成零依赖纯 TS 包端侧运行，费率库 SQLite 落地并强制版本化，一期不要服务器。** 选定之后不要再改技术栈——这个项目的风险不在技术选型，在费率数据的准确性与口径确认。
