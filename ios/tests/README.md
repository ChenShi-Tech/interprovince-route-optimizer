## 必须有的专项用例

这些是本项目历史上真实踩过的坑，或最容易漏的口径：

| # | 用例 | 防的是什么 |
|---|---|---|
| 1 | **送出省输电价格出现在成本拆解中** | 这是最常被漏掉的一项费用，靠代码审查抓不住 |
| 2 | **对向通行的边，路径标识不碰撞** | 边的存储方向与行进方向相反，用 from/to 做标识会撞 |
| 3 | **绕行度 / 跳数上限生效** | 否则会算出绕行大半个中国的荒谬路径 |
| 4 | **容量制工程不被按 0 计** | 按 0 计会让容量制通道在比选中被系统性高估 |
| 5 | **乘性网损 vs 加性边权有可观察差异** | 验证网损确实走的是两步法，而非被当成边权 |
| 6 | **缺字段立即报错** | 防止 `convertFromSnakeCase` 让漏字段静默变 `nil`，表现为"算得偏小" |
| 7 | **非 `gov` 段触发告警** | 报备价与核定价不得混同 |
| 8 | **`priceVersion` 不一致时拒绝计算** | 两端版本不一致会让同一笔交易出现两个落地价，比算错更难排查 |

## 比对纪律

| 字段 | 容差 |
|---|---|
| **路径节点序列** | **必须完全一致**（字符串枚举，无容差） |
| 落地成本 / 过网费 / 送端净收益 / 送达系数 | `1e-4` |

**路径序列不能用容差。** 容差放过它，会让"走的完全不是同一条路但钱差不多"这种情况溜过去——而这恰恰是要抓的问题。

**两端不一致时的排查顺序：先怀疑浮点与舍入，再怀疑算法。** 定位方式是逐段拆解比对，找到第一个分歧点。

---

## 基线是可以重新生成的

改了费率或通道数据后，用 `node tools/baseline2.mjs` 重新生成基线，再跑两端比对。

⚠️ **基线绑定费率快照（含 sha256），不能跨费率版本混用。**
