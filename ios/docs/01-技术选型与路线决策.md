## 一、先看三条候选路线

| | **A · WKWebView 壳** | **B · SwiftUI 原生** | **C · React Native** |
|---|---|---|---|
| 做法 | 把现有 `index.html` 装进 WKWebView | 用 Swift 重写界面，算法重写为 Swift Package | 与安卓共用一套 RN 代码 |
| 出包速度 | **1–2 天** | 数周 | 数周（但不重写算法） |
| 与 Web 一致性 | **天然一致**（同一份代码） | 需回归保证 | 需回归保证 |
| 算法 | 直接复用 JS | 重写为 Swift，需重建回归 | 复用 TS 包 |
| 离线能力 | ✅ 数据已内联，天然离线 | ✅ | ✅ |
| 苹果生态能力（Widget / Face ID / App Intents / 分享扩展） | **基本没有** | **最强** | 中等（需桥接） |
| 走 App Store | ❌ **审核指南 4.2 高风险** | ✅ | ✅（风险低于 A） |
| 长期维护成本 | 一个壳，但两端各自维护 | iOS 独立一套 | **与安卓共用一套** |
| 团队上手成本 | 几乎为零 | 需学 Swift | 需学 RN |

## 二、一个决定性事实：iOS 的地图天花板与路线无关

`src/app/ui/map.js` 第 147 行：

> 判断当前是否运行在带腾讯地图代理的环境里（WorkBuddy 本地预览）。
> 托管到外网后代理不可用，必须改用天地图或内置拓扑图，否则底图会是一片空白。

腾讯地图走的是 WorkBuddy 预览环境注入的本地代理（`http://127.0.0.1:__WB_HTTP_PORT__/...`）。**任何 iOS 形态下都不存在这个代理**——不论是 WebView 壳还是原生。所以三条路线在地图上是同一个天花板：

- **内置 SVG / Canvas 拓扑图**：完全离线，永远可用，是兜底也是主力；
- **天地图**：需要用户自己在应用内粘贴 tk。

**这条不构成选型差异**，但它把「地图页不得空白」变成了硬验收项，写进了阶段 3。

## 三、本项目的既有资产盘点

选型的真正依据不是技术先进与否，而是**哪些资产能被复用**。

| 资产 | 位置 | 能否复用 |
|---|---|---|
| 自包含 Web 版 | `index.html`（单文件，数据内联） | ✅ A 路线可直接装进 WKWebView |
| 端云共用数据 | `shared/app-data.json` / `.min.json` | ✅ 三条路线都能读 |
| 算法层（纯函数、零依赖） | `src/app/algo/`：`network.js` / `cost.js` / `paths.js` / `solve.js` | ✅ A 直接跑；C 可搬进 TS 包；B 需重写 |
| 回归基线 | `docs/regression-baseline-v2.json`（503 省对 / 1739 路线） | ✅ 三条路线都必须跑 |
| 数据契约 | `docs/03-数据接口说明.md` | ✅ 与实现语言无关 |
| 安卓壳工程 | `android/`（`build-apk.mjs`） | A 路线的 iOS 版可对称实现 |
| 现有 RN 工程 | **不存在** | ⚠️ 阶段 2 建议的 `packages/route-engine` 也**尚未抽出** |

**最后一行很关键**：C 路线的前提是「与安卓共用一套 RN 代码」，但目前安卓侧只有 WebView 壳，RN 工程尚未开始。**所以 C 路线不是"复用"，而是"同时开两条 RN 工程"**，成本被普遍低估。

## 四、推荐：A 先行，B 为主力

### 为什么先 A

1. **成本几乎为零。** `index.html` 已经是自包含单文件（数据内联、无后端、无网络依赖），WKWebView 直接加载即可。相比安卓那边的 gradle 打包，iOS 的壳工程更简单。
2. **能立刻拿到真实反馈。** 交易员用了之后提的意见，才是决定 B 路线做哪些页面的依据。先做 B 等于在不知道要什么的情况下重写一遍。
3. **离线天然成立。** Web 版本身就不依赖网络，装进壳里依然离线可用——这一点恰好绕开了 WKWebView 在 `file://` 下的资源加载沙箱限制。

### 为什么 B 才是长期答案

1. **苹果生态能力只有 B 能拿到。** Widget、Face ID、App Intents、分享扩展——这些是"手机上比浏览器强在哪"的答案。A 路线一个都拿不到。
2. **审核指南 4.2 的硬门槛。** 若将来要上 App Store，WebView 壳会被判定为「重新打包的网站」。**B 是唯一没有这个包袱的路线。**
3. **团队规模允许。** 这个工具的需求边界清晰（输入 → 算 → 看拆解 → 改费率），不需要为了跨端一致性牺牲原生体验。

### 什么情况下改选 C

只有在**明确不做 iOS 战略投入、且安卓 RN 工程确实要先行落地**时才考虑。此时 iOS 的边际成本才真的接近零。**否则 C 是三条路线里总成本最高的。**

## 五、不推荐的路

| 路线 | 否决理由 |
|---|---|
| Flutter | 算法要用 Dart 全部重写，等于把唯一经过实测验证的逻辑（修掉过对向边方向错误、跳数绕行失控两个真实缺陷）重新引入风险。安卓侧 `docs/01-安卓开发框架.md` 已做过同样判断 |
| 原生 UIKit + Objective-C | 无理由。SwiftUI 是当前默认 |
| 跨端小程序 | 交易员场景要的是可侧载、可离线的独立 App；小程序解决不了离线 |
| Apple Maps 做业务底图 | 地图白名单是腾讯 / 天地图 / 高德 / 百度。省界由合规底图负责 |
