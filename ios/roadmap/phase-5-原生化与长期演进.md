# 阶段 5 · 原生化与长期演进

> 周期：按需启动 ｜ 里程碑：**M5 · 好用** ｜ 前置：阶段 4 完成，且已有真实使用反馈

---

## 一、核心目标

从「能装」到「好用」，并回答一个迟早要回答的问题：**数据要不要出端**。

这一阶段**不应在需求被验证之前启动**。它的每一项都应由真实使用中暴露出的痛点驱动，而不是「iOS 上应该有」的清单。

---

## 二、关键技术点与所需技能

### 2.1 原生能力（按性价比排序）

| # | 能力 | 价值 | 要素 |
|---|---|---|---|
| 1 | **Widget** | 常用省对的落地价在主屏一目了然，这是 Web 完全做不到的 | WidgetKit、Timeline 与刷新策略 |
| 2 | **Share Extension** | 把测算结果一键丢进钉钉 / 企业微信——你们的协作链路已经在这 | ShareLink、`NSExtension` |
| 3 | **Face ID 锁定** | 费率库与历史测算属于敏感信息 | LocalAuthentication |
| 4 | **App Intents / Siri** | 快捷指令触发常用测算 | App Intents 框架 |

⚠️ **若考虑上架 App Store**，这四项也是通过审核指南 **4.2 Minimum Functionality** 的关键——WebView 壳会被判为「重新打包的网站」。审核方要求至少三项真正的原生能力外加离线支持。**但若只做内部分发，则不受此约束**，做与不做纯看用户价值。

### 2.2 数据同步：一个必须慎重回答的问题

引入同步意味着引入服务端，而**引入自建服务端域名会让 App 备案从「不需要」变成硬前置**（见 [`docs/05-分发与合规.md`](../docs/05-分发与合规.md)）。所以先问：**真的需要吗？**

| 需求 | 结论 |
|---|---|
| 多人共用同一份费率库 | ✅ 需要 |
| 变更留痕与审计 | ✅ 需要 |
| 行情自动同步 | ✅ 需要 |
| 只是想让用户自己带费率走 | ❌ 不需要——`fileExporter` 导出一个 json 就够了 |

若确实需要，**优先 CloudKit 私有库**（无需自建域名，规避备案触发），再考虑自建服务端。

### 2.3 跨端一致性

`packages/RouteEngine` 的 Swift 版与 Web/安卓的 TS 版必须**共用同一份基线做回归**：

- 同一输入 → 同一输出，容差 `1e-4`；
- **两端出现分歧时，先怀疑浮点与舍入，再怀疑算法**；
- 建议把「两端跑同一组基线并比对」做成一条可重复执行的脚本，落在 `ios/tools/`。

### 2.4 长期：两套市场模型的引擎位置

这个项目迟早会碰到国网与南网模型不兼容的问题，**在 iOS 上要提前把扩展点留出来**：

| | 国网省间现货 | 南网区域市场 |
|---|---|---|
| 建模方式 | **交易路径**（与本项目图模型一致，规则原文：一对节点间优先选输电价格最低的路径） | **无交易路径概念** |
| 约束 | 路径成本 + 绕行度 + 跳数上限 | 断面极限功率 + GSDF 灵敏度 |

因此 `RouteEngine` 的求解入口应设计为**面向协议的**（`protocol RouteSolver`），让两套引擎可并列实现，而不是把国网逻辑写死在调用的地方。

## 三、交付物

- Widget / 快捷指令 / 分享扩展 / Face ID **至少落地两项**；
- **跨端回归报告**：同一组基线在 Web 与 iOS 上的输出比对结果；
- 若启动同步：数据模型与服务端接口设计文档 + 备案前置评估。

---

## 四、验收标准

| 项 | 判定 |
|---|---|
| 跨端一致 | 两端同输入同输出，1739 条基线在 `1e-4` 内一致 |
| 性能 | Widget 冷启动 < 1 s |
| 备案前置 | 若引入自建域名，App 备案已完成或已启动 |
| 扩展点 | `RouteEngine` 的求解入口是协议化的，新增模型不改调用方 |

---

## 五、风险

| 风险 | 应对 |
|---|---|
| 过早引入服务端，背上一堆运维 | 用"是否需要多人共用 + 留痕 + 自动同步"三问做闸门 |
| 引入自建域名触发 App 备案 | 优先 CloudKit；若必须自建则把备案排进工期 |
| 两端算法长期分叉 | 基线比对做成脚本，纳入常规流程而非一次性动作 |
| 南网模型进来时架构撑不住 | 求解入口协议化，两套引擎并列 |
| 为"iOS 应该有"而做的功能没人用 | 每项native能力都要有真实使用反馈作为依据 |
